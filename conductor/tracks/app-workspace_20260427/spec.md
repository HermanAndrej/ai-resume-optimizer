# Specification: Application Workspace

**Track ID:** `app-workspace_20260427`
**Type:** Feature
**Created:** 2026-04-27
**Status:** Draft

## Summary

Turn each saved application from a static analysis snapshot into an editable "workspace": display the JD, expose application metadata (status, notes, source URL), detect when the profile has changed since analysis, and allow re-running analysis in place.

## Context

`compat-analysis_20260426` introduced the `applications` table and the analyze flow. It saves the JD, the compatibility analysis, and a profile hash — but currently the JD is invisible on the show page, the profile hash is unused, and there's no way to edit or update an application after creation. This track closes those gaps.

## User Story

As the user, I want each saved application to be a living workspace I can review, annotate, and refresh, so that analyses stay relevant as my profile evolves and so that I can track where each application stands in my job search pipeline.

## Acceptance Criteria

- [ ] Show page displays the original job description (collapsed panel, expandable to full text)
- [ ] Show page displays application status (analyzed / applied / interviewing / rejected / offer), notes, and source URL with badge + link
- [ ] User can edit status, notes, source URL, and the JD itself from the show page
- [ ] When the current profile hash differs from the saved `profile_snapshot_hash`, a stale-analysis banner appears on the show page with a "Re-analyze" button
- [ ] "Re-analyze" runs keyword + LLM analysis again, persists the new analysis, updates the profile_snapshot_hash, and bumps `updated_at`
- [ ] User can archive an application; archived applications are hidden from the list page by default with a "Show archived" toggle
- [ ] List page shows the status badge for each application
- [ ] All routes have unit + TestClient coverage; full suite green

## Dependencies

- `compat-analysis_20260426` (complete) — uses its `applications` table, `application_repo`, `keyword_analysis`, `compat_scorer`

## Out of Scope

- Tailored resumes per application (separate future track)
- Chat / pending-suggestions integration (separate future track)
- Per-application cost dashboard
- Bulk operations (bulk archive/delete)
- Search / filter beyond archived/active toggle
- Hard delete (only archive)

## Technical Notes

- Schema: migration v2 adds `status TEXT DEFAULT 'analyzed'`, `notes TEXT`, `source_url TEXT` columns to `applications`. `archived` and `updated_at` columns already exist.
- Status enum (validated app-side, not DB constraint): `analyzed`, `applied`, `interviewing`, `rejected`, `offer`
- Stale detection: compute SHA-256 of current `flatten_profile(db)` output (truncated to 16 chars, matching what's stored on creation), compare to `profile_snapshot_hash`. Equal → fresh; differ → stale.
- Re-analyze: extract the analysis pipeline (`flatten_profile` → `compute_overlap` → `score_compatibility`) into a helper used by both POST /applications and POST /applications/{id}/reanalyze.
- All edit forms post to dedicated routes (POST /applications/{id}/edit, /archive, /reanalyze) and 303-redirect back to /applications/{id}.
