# Specification: Profile UI

**Track ID:** `profile-ui_20260423`
**Type:** Feature
**Created:** 2026-04-23
**Status:** Draft

## Summary

Build the 8-section profile editor — a server-rendered Jinja2 + HTMX interface where the user can create and edit every part of their profile. Explicit save per section, with an unsaved-changes warning on navigation.

## Context

The profile is the source of truth for every tailored resume. The user edits it here once, then references it from every per-job application. This track produces the first user-facing UI in the app and establishes the full Jinja2 + HTMX pattern that the rest of the MVP will follow.

## User Story

As a job seeker, I want to maintain my entire professional profile in one place with clearly-separated, explicitly-saved sections so that I never lose edits and always have a single source of truth to tailor resumes from.

## Acceptance Criteria

- [ ] All 8 sections editable in the browser: Personal Info (+ links), Summary, Experience (+ bullets), Education, Skills (categorized), Projects (+ bullets), Certifications, Custom Sections
- [ ] Each section has its own form with an explicit **Save** button — no autosave
- [ ] Attempting to navigate away with unsaved edits triggers a confirmation prompt
- [ ] Saved data is persisted to SQLite; reloading the page shows the saved state
- [ ] Add/remove works for list items (experience entries, bullets, skill categories, etc.)
- [ ] The navigation shell lists all 8 sections on the left; active section is highlighted
- [ ] Pydantic v2 models validate every request; invalid input surfaces inline errors

## Technical Notes

- **Stack:** Jinja2 templates + HTMX for form submission and partial HTML swaps. Plain CSS only — no Tailwind, no component libraries.
- **Dirty tracking:** a small client-side script listens for input/change events on the main form and sets a page-level dirty flag; `beforeunload` shows the browser's built-in confirmation dialog. Dirty flag cleared on successful save.
- **Endpoints:** `GET /` redirects to `/profile/personal`. Each section exposes `GET /profile/{section}` (render) and `POST /profile/{section}` (save). List sub-resources get their own endpoints for add/remove.
- **Profile row:** seeded during scaffolding with `id=1`; all section data hangs off it via foreign keys.
- **Repository layer:** `backend/services/profile_repo.py` centralizes all SQL so route handlers stay thin. List sync strategy: delete-all-then-insert per section (simple, safe, fine for MVP scale).
- **Error surfacing:** validation errors re-render the form with field-level messages; no JSON responses to the browser.
- **HTMX idiom:** form POST with `hx-post` → server responds with the refreshed section partial. Add row: `hx-post` returns just the new row HTML. Remove row: `hx-delete` returns empty, HTMX removes the target.
